八个比特一捆

一个比特太小，干不了什么事。电脑通常把八个比特捆成一捆来用，这一捆叫一个字节（byte）。一个字节有 28 = 256 种样子，可以表示 0 到 255 的一个数，或者一个英文字母、一个数字、一个标点（第五章讲怎样表示）。

为什么是八个？早年的电脑各有各的捆法，六个、七个、九个都有。1964 年，IBM 推出 System/360 系列电脑，规定一个字节就是 8 位；这个系列卖得极好，大家就都跟着用了。8 还是 2 的整数次方，切成两半是 4 位，正好配十六进制。

十六进制：给人看的二进制

二进制对电脑方便，对人眼太累：1011010011110001，数都数不清。于是人们每 4 位分一组，每组换成一个符号。4 位有 16 种样子，0 到 9 不够用，就借 A、B、C、D、E、F 表示 10 到 15。这就是十六进制（hexadecimal，常简称 hex）。

二进制00000001…1001101010111100110111101111
十六进制01…9ABCDEF
十进制01…9101112131415

上面那串就变成：1011 0100 1111 0001 → B4F1。一个字节正好是两个十六进制数字，从 00 到 FF。为了不和十进制搞混，程序里写十六进制常在前面加 0x：0xFF 就是 255。网页上的颜色 #FF8800 也是十六进制，三个字节分别是红、绿、蓝（第六章）。

只要背熟 A 到 F 是 10 到 15，再记住 8、4、2、1 四个位权，二进制和十六进制就能心算互换：C 是 12 = 8 + 4，所以是 1100。

文件就是一串字节

你电脑里的每一个文件，照片、歌、Word 文档、游戏存档，打开来看，都只是一长串字节。区别只在于怎样“读”这串字节：当成文字读，当成像素读，还是当成声音读。下面亲眼看看。

拿放大镜看一个文件10 分钟
  1. 在终端里进入练习文件夹，建一个只写着 hello 的文件： 
    % cd ~/base
% echo hello > hi.txt
% ls -l hi.txt
-rw-r--r--  1 you  staff  6 11 28 20:00 hi.txt
    中间那个 6 是文件大小：6 个字节。可是 hello 只有 5 个字母？
  2. 用 xxd 看每一个字节： 
    % xxd hi.txt
00000000: 6865 6c6c 6f0a                           hello.
    最左边 00000000 是“从第几个字节开始”；中间每两个十六进制数字是一个字节：68 是 h，65 是 e，6c 是 l……最后多出来的 0a 就是第六个字节：换行。echo 在末尾自动加了一个换行。右边是把这些字节当成文字的样子，认不出的字节显示成点。
  3. 再试一个：echo -n hello | xxd（-n 表示不加换行），这回只有 5 个字节。

KB、MB、GB

字节多了要用大单位。按国际单位制，千（K）是 1000，兆（M）是一百万，吉（G）是十亿。可是电脑喜欢 2 的整数次方，210 = 1024 正好接近 1000，所以很多年里人们也把 1024 字节叫 1 KB。于是同一个“KB”有两种意思，至今还在打架：

  • 内存一般按 1024 算：你的 8 GB 内存 = 8 × 1024 × 1024 × 1024 = 8589934592 字节。第零章那个怪数就是这么来的。
  • 硬盘厂商按 1000 算：标着 512 GB 的硬盘，是 512000000000 字节左右。
  • Mac 的“关于本机”和访达，从 2009 年起也改成按 1000 算，所以和硬盘盒子上写的对得上；Windows 按 1024 算却仍然写 GB，于是同一块硬盘在 Windows 上显得“缩水”了。
两件小侦探活
  1. 回到第零章记下的内存字节数，除以 1024 三次，看看是不是正好等于你的内存 GB 数。
  2. 在终端里输入 echo -n 你好 | xxd，数一数两个汉字一共占几个字节。第五章揭晓为什么。

一个字节有几个比特？

0xFF 是十进制的几？

F 是 15，15 × 16 + 15 = 255，也就是一个字节最大的数。

十六进制 C 写成 4 位二进制是？

C 是 12 = 8 + 4：1100。

  2. 3
  3. 16

h、i，再加 echo 自动补的换行 0a，一共 3 个字节。

  3. Windows 占掉了

两套前缀和两种“每秒”

1998 年国际电工委员会（IEC）定了一套二进制前缀：KiB = 210、MiB = 220、GiB = 230、TiB = 240，而 KB、MB 回归 103、106。Linux 的不少工具和 macOS 的部分命令会写 KiB、Gi，教材和考题却大多还写 KB 并按 210 算。做题时的习惯：说容量（主存、Cache、页）按 2 的幂，说速率（主频、带宽、传输率）按 10 的幂，题目另有说明的从说明。

还要分清小写 b 和大写 B：b 是比特，B 是字节。家里宽带“100 Mbps”是每秒 100×106 比特，除以 8 才是 12.5 MB/s，这就是下载速度看起来只有十几兆的原因。

字、字长、编址

字长是 CPU 一次能处理的二进制位数，通常等于通用寄存器的宽度。Apple Silicon 是 64 位，寄存器 64 位，地址也按 64 位算。字的长度没有统一规定：408 题里一个“字”可能是 16 位或 32 位，要看题目；x86 的老传统里 word 是 16 位；ARM 的 word 是 32 位。

现代机器几乎都按字节编址：每个地址对应一个字节，一个 4 字节的整数占四个连续地址，它的“地址”指最小的那个。按字编址的机器（每个地址一个字）在考题里也会出现，换算时注意：容量 ÷ 编址单位 = 地址个数，log2(地址个数) = 地址位数。

大端和小端

一个多字节的数放进按字节编址的内存，先放哪头？0x12345678 存在地址 0x100 开始的四个字节里：

  • 大端（big-endian）：高位字节放低地址。0x100 → 12，0x101 → 34，0x102 → 56，0x103 → 78。像人写数字一样“从大头开始”。网络协议规定在线上传输时用大端，所以大端也叫“网络字节序”。
  • 小端（little-endian）：低位字节放低地址。0x100 → 78，0x101 → 56，0x102 → 34，0x103 → 12。x86 和 Apple Silicon（ARM 在 macOS 下运行于小端模式）都是小端。

字节序只影响“多字节的数在内存里的排法”，不影响一个字节内部的比特顺序，也不影响字符串（字符串本来就是一个字节一个字节按顺序放的）。

大端还是小端

输入一个十六进制数，选它占几个字节，看它在两种机器的内存里怎样排。下面是同一串字节被“读错字节序”时会变成什么数。

问问本机是哪一端5 分钟
>>> import sys
>>> sys.byteorder
'little'
>>> (0x12345678).to_bytes(4, 'little').hex(' ')
'78 56 34 12'
>>> (0x12345678).to_bytes(4, 'big').hex(' ')
'12 34 56 78'
>>> int.from_bytes(bytes([0x78, 0x56, 0x34, 0x12]), 'big') == 0x78563412
True

第三部学了 C 以后，还会用指针直接看一个 int 的第一个字节是多少。

典型题 · 原创

某计算机按字节编址、采用小端方式。一个 32 位整数 x = 0xA1B2C3D4 存放在地址 0x2000 开始的单元中，一个 16 位整数 y = 0x00FF 紧随其后存放。问：（1）地址 0x2001 中的字节是什么？（2）地址 0x2004 中的字节是什么？（3）如果改成大端，这两个地址中分别是什么？

看解答

小端低位在低地址：0x2000 D4，0x2001 C3，0x2002 B2，0x2003 A1；y 从 0x2004 开始：0x2004 FF，0x2005 00。所以（1）C3，（2）FF。

大端：0x2000 A1，0x2001 B2，0x2002 C3，0x2003 D4，0x2004 00，0x2005 FF。（3）B2 和 00。

面试题

怎样用 C 判断本机是大端还是小端？网络编程里为什么要 htonl？

看要点
unsigned int x = 1;
if (*(unsigned char *)&x == 1) puts("little"); else puts("big");

取 x 的地址，当成指向单个字节的指针，看最低地址那个字节：是 1 说明低位在低地址，小端。（也可以用 union。）网络协议规定多字节字段用大端传输，主机可能是小端，所以发送前用 htonl / htons（host to network long / short）转换，接收后用 ntohl / ntohs 转回来；在大端主机上它们什么也不做。

小端机器，0xA1B2C3D4 存在 0x10 开始的四个字节，地址 0x11 的字节是？（只写两位十六进制）

小端：0x10 D4，0x11 C3。

100 Mbps 的网络，理想情况下每秒能传多少 MB（按 106）？

100 ÷ 8 = 12.5。

“网络字节序”指的是？

  1. 小端
  2. 随机
  3. 大端

网络协议规定用大端。

主存容量 1 MB，按字节编址，地址至少要几位？

1 MB = 220 字节，220 个地址，20 位。

同样 1 MB 主存，字长 16 位、按字编址，地址至少几位？

一个地址对应 2 字节，地址个数 220 ÷ 2 = 219，19 位。

字符串 "AB" 在大端和小端机器的内存里排列一样吗？

  1. 不一样，小端会倒过来
  2. 一样，字符串是一个字节一个字节按顺序放的

字节序只管一个多字节的数内部怎样排。

文件开头的魔数

既然文件都是一串字节，程序怎样知道一个文件是图片还是压缩包？靠后缀名（.png）只是约定，随便就能改。更靠得住的是文件开头的几个固定字节，叫魔数（magic number）。file 命令就是查一张魔数表来认文件的。

格式开头的字节备注
PNG89 50 4E 47 0D 0A 1A 0A中间三个是 “PNG”
JPEGFF D8 FF
ZIP50 4B 03 04“PK”，作者 Phil Katz 的缩写；.docx .xlsx .jar 其实都是 ZIP
PDF25 50 44 46“%PDF”
ELF（Linux 程序）7F 45 4C 460x7F 加 “ELF”
Mach-O 64 位（Mac 程序）CF FA ED FE就是小端写下的 0xFEEDFACF
通用二进制（Mac）CA FE BA BE一个文件里装着几种处理器的程序；Java 的 .class 文件也用这个魔数

PNG 那八个字节是精心设计的：第一个字节 0x89 最高位是 1，如果文件经过只能传 7 位的老式通道，这一位被抹掉，一眼就能发现；接着的 “PNG” 让人用文本编辑器打开也认得出；0D 0A（回车换行）和后面单独的 0A，用来发现传输途中换行被自动转换过；1A 在老的 DOS 里表示“文件结束”，用 type 命令显示 PNG 时会在这里停下，不会把乱码刷满屏幕。

认几个文件5 分钟
% file /bin/ls
/bin/ls: Mach-O universal binary with 2 architectures: …
% xxd -l 16 /bin/ls
00000000: cafe babe 0000 0002 …
% cp hi.txt fake.png && file fake.png
fake.png: ASCII text

-l 16 只看前 16 个字节。/bin/ls 是一个通用二进制，开头是大端写的 0xCAFEBABE，后面的 2 表示里面装了两种处理器的版本（英特尔和 Apple Silicon）。把文本文件改名叫 fake.png 骗不过 file。

两个词的来历

“byte”是 IBM 的维尔纳·布赫霍尔茨 1956 年在设计 Stretch 计算机时起的，故意把 bite（咬一口）改拼成 byte，免得和 bit 看错。那时一个 byte 的位数还不固定。正因为 byte 曾经不一定是 8 位，网络标准里至今用 octet（八位组）来指“正好 8 位”。

“大端、小端”出自《格列佛游记》：小人国为吃鸡蛋该先敲大头还是小头打了一场仗。1980 年，丹尼·科恩写了一篇《论圣战，并呼吁和平》，借这个典故讽刺工程师为字节序吵个不停，这两个词就这样留了下来。这件事本身也是一个教训：两种做法各有道理时，重要的不是谁对，而是大家约定好一种（网络字节序）。

出处与延伸
  • PNG 规范（W3C / ISO 15948）中 “PNG file signature” 一节的设计说明。
  • Danny Cohen, “On Holy Wars and a Plea for Peace”, IEN 137, 1980。
  • macOS 上 man file、man xxd；/usr/include/mach-o/loader.h 和 fat.h 里定义了 Mach-O 的魔数（装了命令行工具后，可在 xcrun --show-sdk-path 给出的目录下找到）。

.docx 文件用 xxd 看开头，最可能是？

  1. 25 50 44 46
  2. 50 4B 03 04
  3. 89 50 4E 47

.docx 是一个 ZIP 压缩包，里面装着一堆 XML 文件。

PNG 魔数第一个字节是 0x89 而不是普通字母，主要为了？

  1. 发现文件被只能传 7 位的通道破坏
  2. 让文件更小
  3. 表示图片的宽度

0x89 最高位是 1，被抹成 0 就能发现。

网络标准里，“正好 8 位”用哪个英文词？

octet，因为早年的 byte 不一定是 8 位。
