出一本书的四步

把一个 C 程序变成能运行的文件，clang 其实做了四步，像出一本书：

  1. 准备（预处理）：把文件开头 #include 说要用的东西抄进来，像把参考资料夹进稿子里。
  2. 翻译（编译）：把 C 翻成汇编（第十四章）。
  3. 排字（汇编）：把汇编翻成一个个字节。
  4. 装订（链接）：一个程序常常分好几个文件来写，还要用到别人写好的东西，比如 printf。最后一步把它们装订成一本书，把“去第几页找 printf”这样的空填上。

装订的时候，要是某一页写着“去找某某”，可是哪儿都找不到某某，就会报错：Undefined symbols，意思是“有个名字找不到”。

Python 程序没有这四步，它是边读边翻的（第十七章）。

把几个文件和别人写好的东西装订成一个程序，这一步叫什么？

链接。

找不到某个名字时，链接这一步会报什么？

  1. Undefined symbols
  2. IndexError

Undefined symbols：有名字找不到。IndexError 是 Python 列表越界的报错。

Python 程序有没有这四步？

  1. 没有，它边读边翻
  2. 有

没有。这四步是“先全部翻好”的语言（比如 C）才有的。

四步

  1. 预处理：处理所有以 # 开头的行。#include 把另一个文件的内容原样抄进来，#define 把名字替换成文字，注释被删掉。输出还是 C 代码，只是长得多。
  2. 编译：把 C 翻译成汇编（第十四章看过）。语法错误、类型错误都在这一步被发现。
  3. 汇编：把汇编翻译成机器码，存成目标文件（.o）。它已经是机器指令了，但还不能运行：里面调用了别的文件里的函数，那些函数在哪儿，它还不知道。
  4. 链接：把几个目标文件和要用到的库拼在一起，把“调用 square”“调用 printf”这些空着的地址填上，生成可执行文件。

一个程序的四步

一个拆成两个 .c 文件的小程序。点上面的每一步，看命令和它的输出（输出是示意，真实的更长）。最后一个按钮演示“忘了链接 util.o”会怎样。

头文件写什么

main.c 要调用 util.c 里的 square，编译 main.c 时编译器只看得见 main.c，它需要知道“有一个叫 square 的函数，参数是一个 int，返回一个 int”，才能检查你调用得对不对、生成正确的指令。这句话叫声明：int square(int x);（没有函数体）。把声明写进一个头文件 util.h，谁要用就 #include 它。函数真正的代码（定义）只写在 util.c 里一份。#include <stdio.h> 也是这样：stdio.h 里只有 printf 的声明，printf 的机器码在系统的 C 库里，链接时才接上。

一步一步编译20 分钟
  1. 在 ~/base 里新建一个文件夹 proj，在里面建三个文件： 
    int square(int x);
    #include "util.h"
int square(int x) { return x * x; }
    #include <stdio.h>
#include "util.h"
#define TIMES 3
int main(void) {
    printf("%d\n", square(TIMES));
    return 0;
}
    自己的头文件用双引号，系统的用尖括号。
  2. 四步分开做： 
    % clang -E main.c | tail -8
% clang -S main.c -o main.s
% clang -c main.c util.c
% clang main.o util.o -o prog
% ./prog
9
    第一条看预处理的结果（只看最后 8 行，前面是 stdio.h 展开的几百行）：TIMES 已经变成了 3。第二条生成汇编 main.s，用 cat main.s 看看里面有没有 bl _square。第三条生成 main.o 和 util.o。第四条链接。
  3. 故意只链接一个：clang main.o -o prog，看报错：Undefined symbols for architecture arm64: "_square", referenced from: _main in main.o。意思是：main.o 用到了 square，可是你给的文件里没有一个定义它。这是最常见的链接错误。
为什么分开编译

改一下 util.c 里的 square（比如改成 x * x * x），这次只需要 clang -c util.c 重新编译它一个，再链接一次，main.o 不用动。想一想：一个有一千个 .c 文件的项目，改了一个文件，分开编译能省多少时间？再想一想：如果你改的是 util.h，哪些文件要重新编译？

符号表和重定位

每个目标文件都带一张符号表，列出它定义了哪些全局符号（函数名、全局变量名）和引用了哪些别人定义的符号。用 nm 查看：T 是定义在代码段的函数，D 是有初值的全局变量（数据段），B 是没初值的全局变量（BSS），U 是“用到了但没定义”。链接器做两件事：符号解析（给每个 U 找到唯一的定义）和重定位（把各个 .o 的代码和数据排进最终文件，算出每个符号的地址，再把所有引用它的指令里空着的地址填上，目标文件里记着“哪些位置要填、填谁的地址”的重定位表）。

可见性：static 和 extern

  • 函数或全局变量前加 static，它就只在本文件可见，不进入链接，别的文件有同名的也不冲突。好习惯：不打算给别人用的都加 static。
  • 两个文件都定义了同名的全局函数或有初值的全局变量，链接时报 duplicate symbol（重复定义）。所以头文件里不能写定义，否则被两个 .c 包含就重复了。
  • 多个文件要共用一个全局变量：在一个 .c 里定义 int counter = 0;，在头文件里声明 extern int counter;。
  • 头文件保护：头文件被间接包含两次会出问题，惯用写法是 #ifndef UTIL_H / #define UTIL_H / … / #endif，或者 #pragma once。

静态库和动态库

静态库（.a，就是一包 .o）在链接时把用到的代码拷进可执行文件：程序大一些，但不依赖外部文件。动态库（macOS 的 .dylib、Linux 的 .so、Windows 的 .dll）只在可执行文件里记下“我需要它”，运行时才由动态链接器装进内存，多个程序共享同一份：程序小、库升级不用重新编译，但库不在或版本不对就运行不了。macOS 上的 C 库就在动态库 libSystem 里，用 otool -L prog 能看到。

408 操作系统把链接分为三种：静态链接（运行前链成一个整体）、装入时动态链接（装入内存时边装边链）、运行时动态链接（执行中用到某模块时才链接，例如用 dlopen 打开插件）。对应的“装入”方式见下一章。

看符号表，做一个静态库，写一个 Makefile20 分钟
% nm main.o util.o
% otool -L prog
% ar rcs libutil.a util.o
% clang main.c -L. -lutil -o prog2 && ./prog2

ar 把 util.o 打包成 libutil.a；-L. 告诉链接器在当前目录找库，-lutil 表示链接 libutil.a。手敲命令太累时，写一个 Makefile（注意命令行前面必须是一个 Tab 键，不能是空格）：

prog: main.o util.o
	clang main.o util.o -o prog
main.o: main.c util.h
	clang -c main.c
util.o: util.c util.h
	clang -c util.c
clean:
	rm -f *.o prog

之后输入 make，它会比较文件的修改时间，只重新编译改过的部分。make clean 删掉生成的文件（只删 .o 和 prog，删之前看清楚这一行写的是什么）。

典型题 · 原创

a.c 中有 int x = 1; static int y = 2; int z; void f(void) { g(); }，b.c 中有 extern int x; void g(void) { x++; }。（1）写出 a.o 的符号表里各全局符号的类型（nm 的字母）。（2）链接 a.o 和 b.o 时，哪些引用需要重定位？（3）如果 b.c 里也写了 int x = 5;，会怎样？

看解答

（1）x：D（有初值的全局变量）；y：static，只在本文件，nm 显示小写 d（局部），不参与链接；z：没初值，B（或 C，“公共符号”，取决于编译选项）；f：T；g：U（用到但没定义）。

（2）a.o 里 f 调用 g 的那条 bl 指令（要填 g 的地址）；b.o 里 g 读写 x 的指令（要填 x 的地址）。

（3）x 有两个强定义，链接时报 duplicate symbol。

可执行文件里有什么

macOS 的可执行文件是 Mach-O 格式（Linux 是 ELF，Windows 是 PE），里面按段（segment）分：__TEXT（只读、可执行：机器码 __text 节、字符串常量 __cstring 节等）、__DATA（可读写：已初始化的全局变量、BSS 等）、__LINKEDIT（符号表、重定位信息、代码签名）。用 otool -l prog 看“加载命令”，size -m prog 看各节大小。下一章讲操作系统怎样按这些段把程序放进内存。

dyld 和共享缓存

macOS 的动态链接器叫 dyld。为了让几百个系统库加载得快，Apple 把它们预先链接好，合并成一个巨大的“共享缓存”文件，所有程序共享映射。所以在新版 macOS 上，你会发现 /usr/lib/libSystem.B.dylib 这样的文件在磁盘上并不单独存在，它们都在共享缓存里。

位置无关代码

动态库每次可能被装到不同的地址（还有第十八章的地址随机化），所以它的代码里不能写死绝对地址。编译成位置无关代码（PIC）：访问全局数据用“相对于当前指令的偏移”（arm64 的 adrp 加 add 正好擅长这个），调用外部函数先跳到一小段“桩”，由它去一张表里查真正的地址，这张表由动态链接器在加载时或第一次调用时填好（Linux 上叫 PLT 和 GOT）。macOS 上的可执行文件默认也是位置无关的，好让整个程序都能随机化地址。

链接时优化和构建系统

分开编译的代价是：编译器一次只看一个文件，没法把 util.c 里的 square 内联进 main。链接时优化（-flto）让编译器在链接阶段重新看一遍所有代码，跨文件优化。大型项目不再手写 Makefile，而是用 CMake、Meson 生成构建脚本，用 Ninja 这类专注速度的工具执行；Xcode 有自己的构建系统。
