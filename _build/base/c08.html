虫子

程序里的错误，叫 bug（虫子）。1947 年，一台计算机出了故障，工程师在一个继电器里找到一只飞蛾，把它贴在了工作日志上。“bug”这个词其实更早就有人用，可这只飞蛾让它出了名。

找虫子、改虫子，叫调试（debug）。会写程序的人，有一大半时间其实在调试。

捉虫

在第八十一章《错》里，你捉过五只虫子，读过 Python 的报错。这一章换一种虫子：程序不报错，可答案不对。这种最难找。

找虫子的四步

  1. 再现：先找到一个每次都会出错的办法。
  2. 缩小：把没关系的部分去掉，换成简单的数，看虫子还在不在。
  3. 猜：说出一个具体的怀疑，比如“我觉得有一个分数没加进去”。
  4. 验证：把变量打印出来看，看猜得对不对。猜错了，就回到第 3 步。

抓一只真虫子

scores = [80, 95, 70]
total = 0
for i in range(1, len(scores)):
    total = total + scores[i]
print('平均分', total / len(scores))

运行，打出“平均分 55.0”。三个分数都不低，平均怎么才 55？

按四步来：

  1. 再现：每次运行都是 55.0，好办。
  2. 缩小：把分数改成 [10, 10, 10]，平均应该是 10，结果打出 6.666……虫子还在。
  3. 猜：是不是有一个分数没加进去？
  4. 验证：在循环里加一行 print(i, scores[i])，看它打出了哪几个。
找到了吗？对答案

只打出了 1 和 2，第 0 个没有加。因为 range(1, 3) 从 1 开始。改成 range(len(scores))，或者干脆写 for s in scores: total = total + s。

让程序一步一步走

用 print 很好使，可每次都要改程序。还有一种工具，叫调试器：它能让程序走到某一行就停下（这叫断点），然后你一步一步往下走，随时看每个变量是多少。

Python 自带的调试器10 分钟

在 avg.py 的循环里加一行 breakpoint()：

for i in range(1, len(scores)):
    breakpoint()
    total = total + scores[i]

在终端里运行 python3 avg.py，它会停下来，出现 (Pdb) 提示符。试试这几个命令，每个打完按回车：

  • p i：看 i 是多少（p 是 print）。
  • p total：看 total 是多少。
  • c：继续走，到下一次断点再停（c 是 continue）。
  • q：不看了，退出（q 是 quit）。

第一次停下时 i 就已经是 1 了：虫子当场被抓住。C 程序在 Mac 上用的调试器叫 lldb，第二层开头有一个能在网页里玩的。

找虫子的四步

程序里的错误叫 bug（虫子），找错误叫调试（debug）。据说这个词和 1947 年一台计算机里真的夹住的一只飞蛾有关（《一块一块》里讲过，那只飞蛾被贴在了工作日志上）。不管多厉害的程序员，调试都按这几步：

  1. 复现：先找到一个每次都能让错误出现的输入。时有时无的错误最难查，先想办法让它稳定出现。
  2. 缩小：把范围缩小到最少的代码。程序的前一半有没有问题？把输入减到最短还会错吗？
  3. 假设：根据看到的现象，猜一个原因。“平均数太大，可能是加进了不该加的数。”
  4. 验证：让程序停下来，看变量，证明或推翻你的猜测。推翻了就换一个猜测。

最简单的“看变量”是在代码里加 printf，把中间结果打出来。它很好用，但每看一个新变量都要改代码、重新编译。调试器能让程序停在任何一行，随便看任何变量，还能一步一步往下走。Mac 上的调试器叫 lldb，它和 clang 是同一个项目（LLVM）里的工具，装命令行工具时已经装好了。

用 lldb 找虫子20 分钟
  1. 建 avg.c（就是下面装置里的程序），用 -g（带调试信息）和 -O0（不优化）编译，先运行一次看到错误的结果： 
    % clang -g -O0 avg.c -o avg && ./avg
  2. 用 lldb 启动它（第一次用时，系统可能会弹窗要你输入密码，允许开发者工具控制进程）： 
    % lldb ./avg
(lldb) b sum
(lldb) run
(lldb) next
(lldb) p s
(lldb) p i
(lldb) bt
(lldb) quit
  3. 最常用的命令：b 行号 或 b 函数名（设断点）、run（运行到断点停下）、next（执行一行，遇到函数调用不进去）、step（执行一行，遇到函数调用钻进去）、p 变量（打印）、bt（调用栈，第二十章的栈帧一层一层列出来）、continue（继续跑到下一个断点）、finish（跑完当前函数回到调用者）、quit。大部分命令都可以只打第一个字母。

更多的 lldb

      
    
        
  • 条件断点：循环一万次，只在第 9999 次出错。br set -l 5 -c 'i == 9999'，只有条件成立时才停。
    • 
        
  • 观察点：某个变量不知被谁改坏了。watchpoint set variable s（或 w s v s），之后任何代码一改 s，程序就停在那一行。查“内存被悄悄改写”类的虫子，它是最强的武器。
    • 
        
  • 看机器：register read 看寄存器（第十四章的 x0、sp、pc）；memory read -s4 -fx -c8 &a 以 4 字节为一组、十六进制显示 a 开头的 8 个数；disassemble 看当前函数的汇编，配合 si（一次一条指令）单步。
    • 
        
  • 崩溃时：程序崩在 lldb 里会自动停下，bt 看是在哪个函数的哪一行、从哪儿调过来的，frame select 2 切到上面某一层看那一层的变量。

段错误怎么查

      
“Segmentation fault”（Mac 上调试器里显示 EXC_BAD_ACCESS）的意思是程序访问了不该访问的地址。按这个顺序查：① 用 -g -fsanitize=address 重新编译运行，大多数越界、释放后使用会被直接点名；② 在 lldb 里运行，崩溃时 bt，找到你自己的代码里最靠上的那一帧；③ 在那一帧 p 出相关的指针，看是 NULL（空指针）、是一个很小的数（多半是空指针加偏移）、还是一个很怪的地址（野指针或被改坏）；④ 如果是递归，看栈有多深（第二十章的栈溢出）。

      
让虫子更早现身

      
assert(n > 0);（需要 #include <assert.h>）在条件不成立时立刻终止并打印位置，把“很久以后在别处出怪事”变成“当场报错”。为每个函数写几个小测试（单元测试），改代码后一键全部跑一遍。如果某个功能以前好好的、现在坏了，用 git bisect 在提交历史里二分查找是哪一次提交引入的（也就是对提交历史做二分查找）。

第三层 · 深入调试器是怎样做到的约 25 分钟软件断点：把一条指令换成陷阱指令；单步；硬件观察点和调试寄存器；调试器怎样控制另一个进程；DWARF 调试信息和 .dSYM；优化过的代码为什么难调。

    

      
断点的秘密

      
你在第 5 行设断点时，lldb 查调试信息，找到第 5 行对应的第一条机器指令的地址，然后把那条指令换成一条陷阱指令（arm64 上是 brk #0，x86 上是 int3），原来的指令先存起来。程序跑到那里，执行陷阱指令，处理器产生异常，操作系统暂停这个进程并通知调试器。你输入 continue 时，调试器把原指令放回去、单步执行这一条，再把陷阱指令换回来，让程序继续跑。所以“断点”其实是调试器在你的程序里偷偷改写了代码（第十三章“指令即数据”的又一次应用）。

      
    
        
  • 单步：处理器有专门的“单步”模式，每执行一条指令就产生一次异常，调试器借此一条一条地走。
    • 
        
  • 硬件观察点：处理器里有几个调试寄存器，可以设置“访问这个地址就产生异常”，不用改代码、不拖慢程序，但数量很少（通常只有几个）。超过数量时，调试器只能用慢得多的软件办法。
    • 
        
  • 控制另一个进程：调试器要读写别的进程的内存和寄存器，需要操作系统给它特权（Linux 上是 ptrace 系统调用，macOS 上是 Mach 的任务端口）。所以 macOS 会要你输入密码授权，系统进程则受第二十三章的系统完整性保护，不让调试。
    • 
      

      
调试信息

      
-g 让编译器生成 DWARF 格式的调试信息：哪个地址对应源文件第几行、每个变量放在哪个寄存器或栈上的哪个位置、类型是什么。在 Mac 上，它们留在 .o 文件里，可执行文件只记着去哪找；发布时用 dsymutil 把它们收集成一个 .dSYM 包，崩溃报告靠它把地址翻译回函数名和行号（叫“符号化”）。开了优化（-O2）以后，变量可能只活在寄存器里、甚至被算掉了，代码行也被重排合并，调试器常显示 “optimized out”，这就是调试时用 -O0 的原因。
