硬盘只认得“第几块”

对硬盘来说，没有文件，也没有文件夹，只有一长排编了号的块（常见 4 KB 一块），能做的只是“读第 n 块”“写第 n 块”。把这些块组织成“名叫作业.txt、有 12345 字节、放在文稿文件夹里”的样子，是操作系统里文件系统的工作。Mac 用的文件系统叫 APFS，Windows 常用 NTFS，Linux 常用 ext4，U 盘常用 exFAT。

名字不在文件里

类 Unix 系统里，一个文件由三部分组成：

  • 数据块：文件真正的内容，散落在硬盘各处。
  • 索引节点（inode）：文件的“档案卡”，记着大小、权限（第七章的 rwx）、主人、修改时间，以及内容放在哪些块里。每个 inode 有一个编号。
  • 目录项：文件夹本身也是一个文件，内容是一张表，每行是“名字 → inode 编号”。

所以打开 ~/base/hi.txt，是先找到 base 这个目录、在它的表里查到 hi.txt 对应的 inode 编号、再从 inode 找到数据块。改名只改目录表里的一行，移动到同一块盘的另一个文件夹只是把这一行从一张表挪到另一张，都与文件大小无关，所以一瞬间完成。拷贝要真的读出所有数据块再写一遍（APFS 有例外，第三层）。删除只是删掉目录里的那一行、把块标成“空闲”，数据还在原地，直到被新数据覆盖，所以误删的文件常常能恢复，要彻底清除则要另想办法。

看 inode，做两种链接15 分钟
% cd ~/base
% ls -i hi.txt
% ln hi.txt hard.txt
% ln -s hi.txt soft.txt
% ls -li hi.txt hard.txt soft.txt
% mv hi.txt hi2.txt
% cat hard.txt
% cat soft.txt
% mv hi2.txt hi.txt

ls -i 显示 inode 编号。ln 做一个硬链接：又一个名字指向同一个 inode，你会看到 hard.txt 和 hi.txt 编号相同，ls -l 第二列的“链接数”变成 2。ln -s 做一个软链接（符号链接）：一个新的小文件，内容是一个路径“hi.txt”，像 Windows 的快捷方式。把 hi.txt 改名后，硬链接照样能读（它不关心名字），软链接却断了（它找不到叫 hi.txt 的文件）。最后一行改回来。

文件描述符

第二十五章 strace 里，openat 返回了一个小整数 3。程序打开文件后，内核在这个进程的“打开文件表”里加一项，返回它的编号，叫文件描述符；之后 read、write 都用这个号码，不用每次再查路径。每个进程一启动就有三个：0 是标准输入（键盘），1 是标准输出，2 是标准错误。shell 里的 > out.txt 就是在运行程序前把 1 号换成了 out.txt，2>&1 是让 2 号跟着 1 号走（第二十七章 time -l 那一行用过）。

链接数和删除

接着上面的实验：rm hi.txt 以后，cat hard.txt 还能读吗？ls -l hard.txt 的链接数变成几？想一想：inode 和数据块什么时候才真的被释放？（答案：链接数降到 0、而且没有进程还开着它的时候。）做完用 mv hard.txt hi.txt 恢复，rm soft.txt 删掉软链接。

三种分配方式

方式怎样记顺序访问随机访问问题
连续分配起始块号 + 长度最快直接算出块号外部碎片（第二十一章）；文件难以增长
隐式链接每块末尾存下一块的指针可以要从头一块一块找一块坏了后面全丢；指针占空间
显式链接（FAT）把所有“下一块”指针集中成一张文件分配表，常驻内存可以在内存的表里跳着找，不用读盘表随磁盘变大而变大
索引分配每个文件一个索引块，列出所有数据块号可以查索引块即得索引块本身占空间；大文件一个索引块不够

大文件的索引块不够用，有三种办法：链接多个索引块、多级索引、混合索引。Unix 的 inode 用混合索引：比如 10 个直接指针直接指向数据块，1 个一级间接指针指向一个装满块号的索引块，1 个二级间接、1 个三级间接。小文件只用直接指针，访问快；大文件才动用间接索引。

最大文件长度：设块大小 B、块号 p 字节，一个索引块能放 n = B / p 个块号，则最大块数 = 直接数 + n + n2 + n3，乘以 B 就是字节数。读文件某个位置要访问几次磁盘：先算它在第几块，判断落在直接、一级还是二级间接范围内，分别要再读 0、1、2 个索引块，再加 1 次读数据块（inode 是否已在内存按题意）。

空闲块和目录

空闲块的管理：位示图（每块一个比特，第七章第三层的位图，块号和位的位置可以互相换算，是 408 的常考计算）、空闲链表、成组链接法（Unix 早期）。目录结构从单级、两级发展到今天的树形（绝对路径和相对路径，《一块一块》第五部讲过），再加上链接就成了无环图。打开文件时，系统维护两级表：每个进程的打开文件表（文件描述符 → 系统表项）和整个系统的打开文件表（读写位置、引用计数、指向内存里的 inode）。

典型题 · 原创

（1）某文件系统块大小 4 KB，块号 4 字节，inode 有 10 个直接指针、一级、二级、三级间接指针各 1 个。最大文件长度约为多少？（2）读该文件偏移 5000000 字节处的数据，inode 已在内存，需要访问几次磁盘？（3）位示图用 32 位的字组成，字号和位号都从 0 开始，第 i 个字第 j 位对应的块号是多少？块号 1000 对应哪个字哪一位？

看解答

（1）n = 4096 / 4 = 1024。最大块数 = 10 + 1024 + 10242 + 10243 ≈ 230，乘 4 KB 约 4 TB（精确值是 (10 + 210 + 220 + 230) × 4 KB）。

（2）块号 = ⌊5000000 / 4096⌋ = 1220。前 10 块是直接，10 到 1033 是一级间接（10 + 1024 = 1034），1220 ≥ 1034，落在二级间接。要读二级索引块、一级索引块各 1 次，再读数据块 1 次，共 3 次。

（3）块号 = 32i + j。1000 = 32 × 31 + 8，第 31 个字的第 8 位。

写到一半断电了

往文件末尾加一块数据，至少要改三处：位示图（这块被占用了）、inode（大小和块列表）、数据块本身。如果只改了一两处就断电，文件系统就不一致了（块被标成已用却没人拥有，或者 inode 指向一块垃圾）。老办法是开机时用 fsck 扫描整个磁盘修复，硬盘越大越慢。日志文件系统（ext4、NTFS、macOS 以前的 HFS+）先把“我要改这三处”写进一块专门的日志区，再真正去改；断电后只要重放或丢弃日志里没完成的那条，几秒就恢复。

写时复制：APFS

2017 年起 Mac 用的 APFS 换了思路：永远不在原地改，要改的块写到新位置，再自下而上更新指向它的元数据，最后一步原子地切换根指针。断电时要么是旧版本、要么是新版本，没有半截。这个设计顺带带来几件好事：

  • 克隆：在访达里拷贝一个文件（同一个 APFS 宗卷内），新文件只是共享原来的数据块，几乎瞬间完成、不占额外空间；以后谁改了哪一块，才复制那一块（又是写时复制）。命令行里 cp -c 显式请求克隆。
  • 快照：把某一刻的根指针保存下来，就得到整个宗卷在那一刻的只读样子，“时间机器”的本地快照和系统更新都用它。
  • 空间共享：一块物理磁盘上的几个宗卷（比如系统宗卷和数据宗卷）共用剩余空间，不必事先分好大小。

写了不等于写到盘上

为了快，write 返回时数据常常只是进了内存里的缓存，过一会儿才真正写到硬盘。程序如果必须确保数据落盘（数据库提交一笔交易），要调用 fsync。在 macOS 上，连 fsync 也只保证交给了硬盘，硬盘自己还有缓存，要彻底落盘得用 fcntl(fd, F_FULLFSYNC)。这种“到底写没写进去”的层层缓存，是数据库工程师每天要和它较劲的事。
