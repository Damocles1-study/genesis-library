count++ 是三步

C 里的 count++ 看起来是一步，翻译成机器指令却是三步（第十四章）：读（把 count 从内存读进寄存器）、加（寄存器加一）、写（把寄存器写回内存）。两个线程同时做，可能这样交错：A 读到 5，B 也读到 5；A 加成 6 写回；B 也加成 6 写回。两个人各加了一次，count 却只多了 1。这种结果取决于“谁先谁后”的错误叫竞态（race condition），会改共享数据的那段代码叫临界区。

两个人同时记账

两个线程都要执行 count++（读、加、写三步），count 一开始是 0。你来当调度器：点“A 走一步”“B 走一步”决定谁先执行，看最后 count 是 1 还是 2。再点“随机交错一千次”看看结果的分布；打开“加锁”再试。

锁

解决办法是规定“同一时刻只许一个线程在临界区里”，叫互斥。最常用的工具是锁（mutex）：进临界区前先上锁，出来时开锁；锁已经被别人上了，就等着。像只有一把钥匙的厕所。C 里用 pthread 库：

#include <stdio.h>
#include <pthread.h>
long count = 0;
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
void *work(void *arg) {
    for (int i = 0; i < 1000000; i++) {
        /* pthread_mutex_lock(&m); */
        count++;
        /* pthread_mutex_unlock(&m); */
    }
    return NULL;
}
int main(void) {
    pthread_t a, b;
    pthread_create(&a, NULL, work, NULL);
    pthread_create(&b, NULL, work, NULL);
    pthread_join(a, NULL); pthread_join(b, NULL);
    printf("count = %ld（应该是 2000000）\n", count);
    return 0;
}
亲手制造一次竞态15 分钟
% clang -O0 race.c -o race && ./race && ./race && ./race
% clang -O0 -g -fsanitize=thread race.c -o race && ./race

运行几次，结果每次都不一样，而且都小于 2000000。第二条用“线程消毒器”编译，它会报告 WARNING: ThreadSanitizer: data race，指出两个线程在哪一行同时读写了 count。然后把两行注释打开（加上锁），重新编译，结果就总是 2000000 了，只是慢了不少：锁是有代价的。

死锁

锁多了又有新麻烦。两个人吃饭，桌上一把刀一把叉，都要刀叉齐了才能吃。甲拿了刀等叉，乙拿了叉等刀，两人都不肯放下，就这样一直等下去，这叫死锁。十字路口四个方向的车都开进路口一半、互相堵死，也是死锁。程序里两个线程各持一把锁、又去要对方那把，就会卡住不动，而且没有报错。最简单的预防办法：大家约好按同样的顺序拿锁（都先拿刀再拿叉）。

临界区的准则和实现

四条准则：空闲让进、忙则等待、有限等待、让权等待（进不去时让出处理器，不要空转）。软件办法有 Peterson 算法（两个线程，用 flag 和 turn 两个变量）；硬件办法有关中断（只适用于单处理器内核）和原子指令：TestAndSet、Swap（交换），用它们做的自旋锁会“忙等”，不满足让权等待。

信号量

信号量 S 是一个整数加一个等待队列，只能用两个原子操作访问：P(S)（wait）：S 减 1，若 S < 0 则把自己阻塞进队列；V(S)（signal）：S 加 1，若 S ≤ 0 则唤醒队列里的一个。S 为负时，其绝对值就是等待的进程数。用法：

  • 互斥：mutex 初值 1，临界区前 P、后 V。
  • 同步（前驱关系，A 做完 B 才能做）：S 初值 0，A 做完 V(S)，B 开始前 P(S)。
  • 资源计数：初值为资源个数。
semaphore mutex = 1, empty = n, full = 0;
producer: while (1) { 生产一个; P(empty); P(mutex); 放进缓冲区; V(mutex); V(full); }
consumer: while (1) { P(full); P(mutex); 取出一个; V(mutex); V(empty); 消费它; }

易错点：P(empty) 和 P(mutex) 的顺序不能颠倒，否则缓冲区满时生产者拿着 mutex 阻塞在 empty 上，消费者拿不到 mutex 取不走东西，死锁。V 操作的顺序则无所谓。读者写者（读者可以同时读，写者要独占）用一个 count 记读者数，第一个读者 P(rw)、最后一个读者 V(rw)；哲学家进餐（五个人五根筷子）的经典解法是限制最多四人同时拿筷子，或奇数号先拿左边、偶数号先拿右边。管程把共享数据和对它的操作封装在一起，同一时刻只允许一个进程在管程内，用条件变量 wait、signal 做同步（Java 的 synchronized 就是这个思想）。

死锁

四个必要条件（缺一个就不会死锁）：互斥、不剥夺、请求并保持、循环等待。对策：预防（破坏某个条件，如一次申请所有资源破坏“请求并保持”、按编号顺序申请破坏“循环等待”）；避免（每次分配前检查分配后是否仍处于安全状态，即存在一个让所有进程都能完成的顺序，银行家算法）；检测与解除（允许发生，定期画资源分配图化简找死锁，再撤销进程或剥夺资源）。安全状态一定不会死锁；不安全状态不一定会死锁，但有可能。

银行家算法

五个进程、三类资源。表里是“已分配”和“最大需求”，下面是“可用”。点“检查安全性”找安全序列；也可以让某个进程提出一个请求，看系统答不答应。表里的数字都能改。

典型题 · 原创

（1）信号量 S 初值为 3，当前值为 −2，有几个可用资源、几个进程在等待？（2）系统有 3 个同类资源，被 n 个进程共享，每个进程最多需要 2 个。n 最大为多少时一定不会死锁？（3）对上面装置里的初始状态，P1 请求 (1, 0, 1) 能否立即分配？P3 请求 (1, 0, 0) 呢？

看解答

（1）没有可用资源，2 个进程在等。

（2）最坏情况每个进程都拿到 1 个、再要 1 个：只要 3 ≥ n × (2 − 1) + 1，即 n ≤ 2 时一定有人能拿齐。n = 2。一般地，m 个资源、n 个进程每个最多要 k 个，n(k − 1) + 1 ≤ m 时不会死锁。

（3）初始状态安全（如 P3、P1、P4、P0、P2）。P1 请求 (1, 0, 1) ≤ 它的需求 (1, 1, 2)，也 ≤ 可用 (2, 2, 1)，但假装分配后可用变为 (1, 2, 0)，没有一个进程的剩余需求能被满足，状态不安全，所以不能分配，P1 要等。P3 请求 (1, 0, 0)：假装分配后可用 (1, 2, 1)，P3 的剩余需求 (1, 1, 1) 能满足，接着 P1、P4、P0、P2 都能完成，安全，可以分配。用装置验证。

原子指令

锁本身是怎么做的？处理器提供“读、改、写一步完成、中间不会被插队”的原子指令。arm64 从 ARMv8.1 起有 ldadd（原子加）、cas（比较并交换：如果内存里还是我以为的那个值，就换成新值，否则失败）等。C11 的 <stdatomic.h> 里，atomic_fetch_add(&count, 1) 在 Apple Silicon 上会编译成一条 ldadd，比加锁快得多。用 clang -O2 -S 可以看到。

内存顺序

更隐蔽的问题：为了快，处理器和编译器会重排读写的顺序（第十五章的乱序执行），单线程看不出来，多线程就可能看到“先写的后到”。x86 的规则比较严格（TSO，第十四章 Rosetta 那一段），ARM 是弱序的，允许更多重排。所以在 Mac 上，一个“在 x86 上从没出过错”的无锁程序可能会出错。正确的做法是用原子变量并指定内存顺序（acquire、release），或者干脆用锁，让编译器和处理器插入必要的屏障。经典的反例是“双重检查锁定”：不加正确的屏障，另一个线程可能拿到一个指针却看到对象还没初始化完。

别抢同一行

第十六章的伪共享在这里正式登场：两个线程各自累加自己的计数器，计数器却挨在同一个缓存行里，两个核为了这一行来回抢，比真共享还慢。把每个线程的计数器放到不同的缓存行（Apple Silicon 上间隔 128 字节），各自算完最后再加起来，常常快得多。更进一步的思路是不共享：Go 语言的口号是“不要用共享内存来通信，要用通信来共享内存”，各线程通过消息队列（channel）传数据。
