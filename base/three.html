      为什么是 C

      C 语言是 1972 年前后丹尼斯·里奇在贝尔实验室为了写 Unix 操作系统而设计的。五十多年过去，它还在一线：macOS 和 Linux 的内核、Python 解释器（官方版本叫 CPython，就是用 C 写的）、数据库、嵌入式设备里的程序，大多是 C 写的。它的特点是离机器很近：一个 int 就是内存里的 4 个字节，一次加法几乎就是一条 add 指令。所以它是看清“程序怎样在机器上跑”的最好窗口。

      编译选项

      平时练习建议：clang -std=c17 -Wall -Wextra -g -O0 x.c -o x。-std=c17 指定标准；-Wall -Wextra 打开警告；-g 带上调试信息（第二十四章）；-O0 不优化，调试时变量不会被优化掉。查函数用法：man 3 printf（第 3 节是 C 库函数）。

      隐式类型转换

      • 整数提升：char、short 参与运算时先变成 int。所以 char a = 100, b = 100; int c = a + b; 得 200，不会在 char 里溢出。
      • 寻常算术转换：两个操作数类型不同时，转成“更大”的那个：int 和 double 运算转成 double；int 和 unsigned int 运算转成 unsigned（第三章的 -1 < 1u 为假就是这个）；int 和 long 运算转成 long。
      • 赋值截断：把大类型赋给小类型，只留低位字节：char c = 300; 得 300 − 256 = 44。把 double 赋给 int，小数部分向零截断：int i = -3.7; 得 −3。
      • 负数的除法和取余：C99 起规定整数除法向零取整：-7 / 2 == -3，-7 % 2 == -1（余数的符号跟被除数）；Python 是向下取整：-7 // 2 == -4，-7 % 2 == 1。在 C 里判断奇数要写 x % 2 != 0，不能写 x % 2 == 1（负奇数不成立）。

      常见的未定义行为

      第三章说过“未定义行为”：标准不规定结果，编译器可以假设它永远不发生。最常见的几种：有符号整数溢出；数组越界（第十九章）；使用未初始化的局部变量；解引用空指针或已释放的指针（第十八、二十一章）；同一个表达式里对一个变量改两次，如 i = i++ + 1;；printf 的格式和参数类型不匹配；除以零。程序“在我电脑上能跑”不代表没有它们。

      典型题 · 原创

      在 Apple Silicon 的 Mac 上（int 32 位、补码），下列各式的值是多少？（1）-17 / 5 和 -17 % 5；（2）(char)200（按 %d 打印，char 有符号）；（3）unsigned int u = 1; int i = -2; 时 u + i（按 %u 打印）；（4）(int)(2.9 + 0.5)；（5）3 / 2 * 2.0。

      看解答

      （1）−3 和 −2（向零取整，余数跟被除数同号，−3 × 5 + (−2) = −17）。

      （2）200 − 256 = −56。（Apple Silicon 上 char 默认有符号；有些平台的 char 默认无符号，这一点标准没有规定。）

      （3）i 转成 unsigned 为 232 − 2，加 1 得 4294967295。

      （4）3.4 向零截断为 3。

      （5）3 / 2 先算，整数除法得 1，再乘 2.0 得 2.0。运算顺序和类型一起决定结果。

      同一个 long，两种大小

      C 标准只规定了各种整数类型的最小范围，没规定确切的字节数。于是不同平台有不同的“数据模型”：macOS、Linux 等类 Unix 系统的 64 位版本用 LP64（long 和指针是 64 位，int 是 32 位）；64 位 Windows 用 LLP64（只有 long long 和指针是 64 位，long 仍是 32 位）。一个在 Mac 上好好的程序，拿到 Windows 上用 long 存文件大小，超过 2 GB 就溢出。跨平台代码的做法是用 <stdint.h> 里的固定宽度类型：int32_t、uint8_t、int64_t，以及表示大小的 size_t、表示指针差的 ptrdiff_t。

      C 的演变

      1978 年，克尼汉和里奇出版《C 程序设计语言》，书里描述的版本人称 K&R C。1989 年美国国家标准学会发布第一个正式标准（C89，次年成为国际标准 C90），之后有 C99（加了 // 注释、bool、可以在 for 里声明变量、变长数组）、C11（线程、原子操作、去掉了危险的 gets）、C17（修订）、C23（true、false、nullptr 成为关键字，规定整数用补码，<stdckdint.h>）。Apple 的 clang 默认采用较新的标准，加 -std= 可以指定。

      clang 是一个“司机”

      你敲的 clang hello.c -o hello 其实依次调用了好几个工具：预处理器、编译器本体、汇编器、链接器（第二十二章一个一个拆开）。加 -v 能看到它实际执行了哪些命令；加 -### 只打印命令不执行。macOS 上的 gcc 命令其实也是 clang（试试 gcc --version），真正的 GCC 要另外用 Homebrew 装。

      变量住在哪儿

      int x = 5; 让程序在内存里找 4 个连着的格子，写进 5（的补码），以后提到 x 就是指这 4 个格子。那它们在第几号？在变量前面加 & 就能问出来：&x 读作“x 的地址”。用 %p 打印地址，会看到一个很长的十六进制数，比如 0x16fdff3ac（64 位地址，第十二章）。

      指针：写着门牌号的纸条

      地址也是一个数，当然可以存进一个变量。专门存地址的变量叫指针（pointer）：

      int x = 5;
int *p = &x;     /* p 是“指向 int 的指针”，里面存着 x 的地址 */
*p = 9;          /* 顺着 p 找到那个格子，把 9 写进去：x 变成 9 */

      两个符号，意思正好相反：&x 是“x 住在哪儿”，*p 是“到 p 写的地址那里去”。int *p 的星号是“p 是个指针”的意思，用的时候 *p 的星号是“顺着找过去”，同一个符号两种用法，一开始容易糊涂，多看几遍下面的装置。指针本身也是变量，也住在内存里，在 64 位的 Mac 上占 8 个字节。

      内存里的变量和指针

      为什么 swap 要传指针

      想写一个函数交换两个变量。最直接的写法 void swap(int a, int b) { int t = a; a = b; b = t; } 不管用：调用 swap(x, y) 时，函数拿到的是 x、y 的复印件（参数是值传递），它交换的是复印件，原件纹丝不动。正确的做法是把地址传进去：swap(&x, &y)，函数里通过 *a、*b 直接改原件。装置里选“swap 两种写法”看看。这也是 scanf("%d", &n) 要写 & 的原因：scanf 要往你的变量里写东西，必须知道它住在哪儿。

      Python 里的变量其实是指针

      Python 的 a = [1, 2, 3] 并不是把列表装进 a，而是在堆上造一个列表，让 a 指向它；b = a 是让 b 也指向同一个列表，所以 b.append(4) 以后 a 也变了。id(a) 在 CPython 里就是那个对象的内存地址。Python 把指针藏了起来，C 把它摊在桌上。

      指针的类型有什么用

      地址只是一个数，为什么指针还要分 int *、char *、double *？因为解引用时要知道“从这个地址开始读几个字节、怎样解释它们”。同一个地址，用 char * 读 1 个字节，用 int * 读 4 个字节。第二章的面试题“用指针判断大小端”就是这样写的。

      指针的加减

      p + 1 不是地址加 1，而是加 sizeof(*p)：int 指针加 1 前进 4 字节，double 指针加 1 前进 8 字节，正好指向“下一个元素”。所以 *(p + i) 就是第 i 个元素，C 里 a[i] 本来就定义为 *(a + i)（下一章）。两个指向同一个数组的指针相减，得到它们之间隔了几个元素（不是字节），类型是 ptrdiff_t。

      几种危险的指针

      • 空指针：int *p = NULL; 表示“哪儿也不指”。解引用空指针是未定义行为，在 Mac 上通常立刻崩溃（Segmentation fault 或 EXC_BAD_ACCESS），因为地址 0 附近的一大片故意不映射。用之前先判断 if (p != NULL)。
      • 野指针：没初始化的指针，里面是随机的地址。
      • 悬空指针：指向的东西已经没了，比如指向一个已经返回的函数的局部变量（第二十章），或者已经 free 的内存（第二十一章）。最难查的一类 bug。
      • void * 是“不说类型的地址”，malloc 就返回它；不能直接解引用，要先转换成具体类型的指针。

      const 放在哪儿

      从变量名往左读：const int *p（或 int const *p）是“p 指向的 int 不能通过 p 改”，p 本身可以指向别处；int *const p 是“p 本身不能改（永远指那一个地方）”，但可以通过它改那个 int；const int *const p 两样都不许。函数参数写成 const char *s，是向调用者保证“我只读不改你的字符串”。

      函数指针和链表

      函数也住在内存里（代码段），所以也有地址：int (*f)(int, int) = add;，之后 f(1, 2) 就调用 add。标准库的 qsort 就靠传入一个比较函数的指针来排任何类型的东西（第十五章 branch.c 里用过）。数据结构课里最常见的指针是链表结点里的 struct node *next;，它把散落在堆上的结点一个一个串起来，下一本书《链与树》从这里开始。

      典型题 · 原创

      设 int a[5] = {10, 20, 30, 40, 50}; int *p = a + 1;，a 的首地址为 0x1000，int 占 4 字节。求：（1）p 的值；（2）*(p + 2)；（3）p[-1]；（4）*p++ 的值以及执行后 p 的值；（5）(char *)p - (char *)a（在第 4 小题执行之后）。

      看解答

      （1）a + 1 前进 4 字节：0x1004。（2）p + 2 指向 a[3]，值 40。（3）p[-1] 即 *(p − 1)，指向 a[0]，值 10。（4）后置 ++ 的优先级高于 *，但它“先用后加”：表达式的值是 *p 即 20，之后 p 变为 0x1008。（5）按字节相减：0x1008 − 0x1000 = 8。若写成 p - a 则是 2（元素个数）。

      这个地址是真的吗

      %p 打出的 0x16fdff3ac 不是内存条上的“第几个字节”，而是虚拟地址：每个程序都以为自己独占一大片从 0 开始的地址空间，处理器和操作系统一起把虚拟地址翻译成真正的物理地址（第二十七章）。所以两个程序里可以有同一个地址，指的却是不同的物理内存。

      为什么每次运行地址都不同

      如果程序每次都把栈、堆、代码放在同样的地址，攻击者利用缓冲区溢出（下一章）时就能预先算好要跳到哪儿。地址空间布局随机化（ASLR）让每次运行时这些区域的起点随机偏移，攻击就难得多。macOS、Linux、Windows、iOS、Android 都默认打开。

      多出来的位：指针签名

      64 位指针有 64 位，但实际的虚拟地址只用了低四十多位，高位是空着的。Apple 从 A12 芯片起在 arm64e 架构上使用 ARMv8.3 的指针认证（PAC）：把指针存进内存前，用一个只有处理器知道的密钥和上下文算出一小段“签名”，塞进指针空着的高位；用之前先验证，签名不对就崩溃。攻击者即使能改写内存里的返回地址或函数指针，也很难伪造出正确的签名。macOS 的系统程序在 Apple Silicon 上就是这样编译的（第二十章还会提到它保护返回地址）。

      严格别名

      第二层说同一个地址可以用不同类型的指针读，但 C 标准其实有限制：一般不允许通过一种类型的指针去读写另一种类型的对象（char 指针例外），这叫严格别名规则。编译器据此假设 int * 和 float * 不会指向同一个地方，大胆优化；违反了就是未定义行为。想看一个 float 的比特，正确的写法是 memcpy 到一个 uint32_t 里，开了优化的编译器会把它变成一条指令，不会真的拷贝。

      二维数组的地址

      int m[R][C] 在 C 里按行存放（行优先）：先放第 0 行的 C 个元素，再放第 1 行……所以 LOC(m[i][j]) = LOC(m[0][0]) + (i × C + j) × L（L 是每个元素的字节数）。Fortran、MATLAB 是按列存放的：LOC = LOC(m[0][0]) + (j × R + i) × L。第十六章说按行遍历快，就是因为 C 按行存。数据结构课的题目常把下标从 1 开始、或者给定 m[1..R][1..C]，套公式前先把下标换成“前面有几个元素”。

      压缩存储：n 阶对称矩阵只存下三角（含对角线），共 n(n + 1)/2 个元素；按行存放时，aij（i ≥ j，下标从 1 开始）在一维数组里的下标（从 0 开始）是 i(i − 1)/2 + j − 1。三角矩阵、三对角矩阵同理推导。这类题的方法都一样：数清楚它前面有几个元素。

      数组和指针

      数组名在大多数表达式里会“退化”成指向首元素的指针，所以 int *p = a; 合法，a[i] 和 p[i] 写法相同。但它们不是一回事：sizeof(a) 是整个数组的字节数，sizeof(p) 是 8；&a 的类型是“指向整个数组的指针”，&a + 1 跳过整个数组；数组名不能被赋值。数组作函数参数时，void f(int a[]) 和 void f(int *a) 完全一样，函数里拿不到数组的长度，所以 C 的函数总要多传一个长度参数。

      字符串函数的坑

      strcpy(dst, src) 不管 dst 有多大，一直抄到 src 的 0 为止，dst 小了就越界；strcat 同理；gets 根本没法限制长度，C11 已经删掉。要用带长度的版本：snprintf(dst, sizeof dst, "%s", src)，或者 macOS 和 BSD 提供的 strlcpy、strlcat（保证结尾有 0）。strncpy 名字像安全版，但源串太长时不会补结尾的 0，是有名的陷阱。

      内存对齐

      处理器读一个 4 字节的 int，如果它的地址是 4 的倍数，一次就能读出来；不是的话，有的处理器要读两次再拼起来，有的干脆报错。所以编译器让每种类型放在它大小的整数倍的地址上（对齐）：char 随便放，short 放在 2 的倍数，int、float 放在 4 的倍数，long、double、指针放在 8 的倍数。结构体的规则：

      1. 每个成员的偏移量必须是它自身对齐要求的整数倍，不够就在前面插填充字节；
      2. 结构体的总大小必须是其中最大对齐要求的整数倍，不够就在末尾填充（这样结构体数组里每个元素也对齐）。

      例：struct { char c; int i; char d; }：c 在偏移 0；i 要 4 的倍数，偏移 1—3 填充，i 在 4—7；d 在 8；总大小要是 4 的倍数，9—11 填充，sizeof 为 12。把字段按从大到小重排成 { int i; char c; char d; }，sizeof 就是 8。装置里的结构体就是前一种。

      典型题 · 原创

      （1）二维数组 double m[10][20] 按行存放，首地址 2000（十进制），m[3][5] 的地址是多少？若按列存放呢？（2）在 Apple Silicon 的 Mac 上（char 1、short 2、int 4、double 8，按自然边界对齐），求 struct A { char a; double b; short c; int d; }; 的 sizeof，并给出一种使它最小的字段顺序。（3）n 阶下三角矩阵（含对角线）按行优先压缩存入数组 B[0..]，aij（1 ≤ j ≤ i ≤ n）存在 B 的哪个下标？

      看解答

      （1）按行：2000 + (3 × 20 + 5) × 8 = 2000 + 520 = 2520。按列：2000 + (5 × 10 + 3) × 8 = 2000 + 424 = 2424。

      （2）a 偏移 0；b 要 8 的倍数，偏移 8—15（1—7 填充）；c 偏移 16—17；d 要 4 的倍数，偏移 20—23（18—19 填充）；总大小 24，已是 8 的倍数，sizeof = 24。重排为 double b; int d; short c; char a; 偏移 0、8、12、14，共 15，补到 8 的倍数为 16。

      （3）第 i 行前面有 1 + 2 + … + (i − 1) = i(i − 1)/2 个元素，本行 aij 前面还有 j − 1 个，下标为 i(i − 1)/2 + j − 1。

      arm64 的栈帧

      Apple Silicon 上（AAPCS64，Apple 略有调整）：前 8 个整数或指针参数放在 x0—x7，返回值放在 x0；x30（LR，链接寄存器）放返回地址，bl func 跳到 func 的同时把下一条指令的地址写进 x30，ret 就是跳回 x30；x29（FP）是帧指针，指向当前栈帧里保存旧 x29 的位置，一串 x29 连起来就能从内往外走遍所有栈帧（调试器的 bt 就靠它）；sp 是栈指针，必须始终 16 字节对齐。一个要调用别的函数的函数，开头结尾通常是这样：

      fact:
    stp  x29, x30, [sp, #-32]!   ; sp 先减 32（栈往下长），把旧 x29 和返回地址存进去
    mov  x29, sp                 ; 新的帧指针
    …                            ; 函数体，局部变量放在 [sp, #16] 之类的地方
    bl   fact                    ; 递归调用：x30 被改写成这里的下一条
    …
    ldp  x29, x30, [sp], #32     ; 恢复旧 x29 和返回地址，sp 加回 32
    ret                          ; 跳回 x30

      因为 bl 会改写 x30，所以凡是要调用别人的函数，都得先把自己的 x30 存到栈上，这就是“返回地址在栈里”的由来。叶子函数（不再调用别人的函数，比如第十四章的 add）可以不建栈帧，直接用 x30 返回。

      谁来保存寄存器：x19—x28 是被调用者保存的，函数如果要用它们，得先把旧值存起来、返回前恢复，所以调用者可以放心地把值留在里面跨调用使用；x0—x18 中的大部分是调用者保存的，被调用的函数可以随便改，调用者如果调用后还要用，得自己先存。

      x86-64 的版本（408 用的是它）

      考研 408 的“程序的机器级表示”以 x86 为例。区别主要在：call f 把返回地址压到栈上（rsp 减 8，再写入），而不是放进寄存器；ret 从栈顶弹出返回地址跳过去。典型的开头和结尾：

      f:  pushq %rbp            # 旧的帧指针压栈
    movq  %rsp, %rbp      # 新帧指针 = 当前栈顶
    subq  $16, %rsp       # 给局部变量留 16 字节
    …                     # 局部变量用 -4(%rbp)、-8(%rbp) 访问
    leave                 # 等于 movq %rbp, %rsp; popq %rbp
    ret                   # 弹出返回地址，跳回去

      Linux 上 x86-64 的参数依次放在 rdi、rsi、rdx、rcx、r8、r9，返回值在 rax。408 题里还会出现 32 位 x86（IA-32），参数全部压栈、用 8(%ebp)、12(%ebp) 取参数（%ebp 上面 4 字节是返回地址，再上面才是第一个参数）。Intel 写法和 AT&T 写法操作数顺序相反，读题先看是哪种。

      （1）某递归函数每层栈帧 48 字节，主线程栈 8 MB（按 8 × 220 字节算，不计其他开销），最多能递归多少层？（2）IA-32 下，函数 int f(int a, int b) 采用标准的 push %ebp; mov %esp, %ebp 开头，进入函数体后，a 和 b 分别在 %ebp 加多少的位置？返回地址在哪里？（3）arm64 下，叶子函数为什么可以不把 x30 存到栈上？

      看解答

      （1）8 × 220 ÷ 48 ≈ 174762 层（实际会少一些，栈里还有 main 和启动代码的帧）。

      （2）调用者先压 b、再压 a（参数从右往左压），call 压返回地址，f 再压旧 %ebp 并让 %ebp 指向它。所以 (%ebp) 是旧 %ebp，4(%ebp) 是返回地址，8(%ebp) 是 a，12(%ebp) 是 b。

      （3）叶子函数不执行 bl，x30 不会被改写，ret 时 x30 里还是调用者给的返回地址。

      如果一个函数的最后一步就是调用另一个函数并直接返回它的结果（return g(x);），当前的栈帧其实已经没用了，可以直接跳到 g，让 g 返回时直接回到我们的调用者。这叫尾调用优化。return n * fact(n - 1); 不是尾调用（调用完还要乘 n），改写成带累加器的 fact_acc(n - 1, acc * n) 就是。用 clang -O2 -S 看，尾递归版里根本没有 bl，只有一个跳回开头的 b。C 标准不保证这种优化，所以不要依赖它防止爆栈；有些语言（Scheme）则规定必须做。

      线程的栈更小

      主线程的栈约 8 MB，但 macOS 上用 pthread 新建的线程，默认栈只有 512 KB。在线程里放一个几百 KB 的局部数组，或者递归深一点，就会爆栈。大数组应该放到堆上（下一章），或者创建线程时用 pthread_attr_setstacksize 指定更大的栈。

      保护返回地址

      第十九章说过，攻击者最想改写的就是栈上的返回地址。除了栈保护（canary），硬件也来帮忙：

      • 指针签名：在 Apple Silicon 的 arm64e 程序里，函数开头多一条 pacibsp（或 paciasp），用密钥和当前 sp 给 x30 签名后再存进栈；结尾用 retab（或 autibsp 加 ret）验证签名后再跳。栈上的返回地址被改了，验签就失败，程序立刻崩溃，攻击者拿不到控制权。
      • 影子栈：英特尔的 CET 等技术在另一块受保护的内存里再存一份返回地址，ret 时两份对不上就报错。

      可以试试：clang -arch arm64e -O1 -S f.c -o -，看看函数开头结尾是不是多了这些指令（arm64e 主要用于系统程序，普通 App 默认编译成 arm64）。

      栈不够用的时候

      栈上的局部变量有两个限制：函数一返回就消失；大小要在写程序时就定下来，而且栈总共只有几 MB。可是很多东西不是这样的：用户要打开一张 4000 万像素的照片（几十 MB），一个游戏要存所有玩家的信息（人数一直在变），一个函数要造一个链表交给别人用（不能随着它返回而消失）。这些东西放在堆（heap）上：一大片由程序自己申请、自己归还的内存。第三部封面的内存地图里，堆在下面、往上长。

      借和还

      #include <stdlib.h>
int n = 1000;                          /* 运行时才知道的长度 */
int *a = malloc(n * sizeof(int));      /* 借 4000 字节，得到它的首地址 */
if (a == NULL) { /* 借不到 */ }
for (int i = 0; i < n; i++) a[i] = i;  /* 当数组用 */
free(a);                               /* 还回去 */
a = NULL;                              /* 好习惯：还了以后别再碰它 */

      malloc（memory allocate）在堆上找一块够大的空地，返回它的地址；free 把它还回去，以后可以再借给别人。借来的内存会一直在，直到你 free 它，或者整个程序结束。Python 的列表、字典、对象都住在堆上，只是 Python 会自己判断“没人用了”再替你还（第三层）。

      三种常见的错

      • 内存泄漏：借了不还。程序越跑越占内存，跑久了把电脑拖慢。浏览器开几天变得很卡，常常就是某处在泄漏。
      • 释放后使用（use after free）：已经 free 了还继续读写。那块内存可能已经借给了别人，你改的是别人的数据。这是最危险的安全漏洞类型之一。
      • 重复释放（double free）：同一块 free 两次，会把分配器自己的账本搞乱。

      这三种错误，程序常常不会马上崩溃，而是在很久以后、很远的地方出现奇怪的症状，非常难查。所以要用工具。

      分配器的账本

      堆是一大块连续的内存，分配器要记住哪些段借出去了、哪些空着。最简单的做法：每块前面放一个头部，写着这块的大小和“已分配 / 空闲”标记，所有块首尾相接，从头部的大小就能跳到下一块（隐式空闲链表）。更快的做法把空闲块用指针串成链表（显式空闲链表），或者按大小分成好几条链（分离空闲链表）。

      • 切分：找到的空闲块比要求的大，把它切成两块，前面借出去，后面仍然空闲。
      • 合并：free 时，如果前后相邻的块也是空闲的，就合并成一大块。往前合并需要知道前一块的大小，所以很多分配器在块的末尾也放一份大小（边界标记）。
      • 对齐：malloc 返回的地址要满足最严格的对齐要求（Mac 上是 16 字节），所以实际分到的往往比要求的多一点。

      四种找空地的办法

      这一节和 408 操作系统里“连续分配管理方式”中的动态分区分配完全是一回事（那里分的是物理内存的分区，这里分的是堆）：

      算法规则空闲分区怎样排特点
      首次适应从头找，第一个够大的按地址递增简单、快；低地址容易留下很多小碎片
      邻近适应（循环首次适应）从上次找到的位置接着往后找按地址，循环分配更均匀；但会把高地址的大空闲区也切碎
      最佳适应所有够大的里面最小的那个按大小递增留下的边角最小，于是产生大量极小、谁也用不上的碎片
      最坏适应最大的那个按大小递减留下的剩余较大还能用，但很快没有大块可用

      没有哪种总是最好。研究和实践表明，首次适应在大多数负载下表现不错，所以常被采用。

      两种碎片

      • 内部碎片：分给你的块比你要的大，多出来的那点在块内部浪费了（头部、对齐、固定大小的分配单位都会造成）。
      • 外部碎片：空闲内存的总量够，但被切成了许多不相邻的小段，没有一段大到能满足请求。可以用紧凑（把已分配的块挪到一起）消除，但 C 的指针直接存着地址，挪了指针就全错了，所以 malloc 不能紧凑；操作系统管理物理内存时可以配合重定位做，代价很大。第二十七章的分页从根本上绕开了这个问题。

      看解答

      首次适应：212 → B（剩 288）；417 → E（剩 183）；112 → B 剩下的 288（剩 176）；426：剩下 A 100、B 176、C 200、D 300、E 183，都不够，失败。

      最坏适应：212 → E 600（剩 388）；417 → B 500（剩 83）；112 → E 剩下的 388（剩 276）；426：最大的是 D 300，不够，失败。

      真实的分配器

      真实世界的分配器比装置复杂得多，思路却相通：把常见的小请求按大小分成若干“级别”（比如 16、32、48……字节），每个级别从专门的页里切同样大小的格子，几乎没有外部碎片、找起来也快；给每个线程或每个核一份本地缓存，多线程不必抢一把锁；大块请求单独向系统要。macOS 的 libmalloc 把小对象分到“tiny”“small”等区域，Linux 的 glibc 用 ptmalloc，Facebook 用 jemalloc，谷歌用 tcmalloc。分配器的选择能让同一个服务器程序的内存占用和速度差出一截。

      谁来还：三种回答

      • 程序员自己还：C。最快、最灵活，也最容易出错。
      • 引用计数：每个对象记着有几个指针指向它，降到 0 就立刻回收。Swift 和 Objective-C 的 ARC、CPython 都用它。弱点是两个对象互相指着（循环引用）时计数永远不为 0，所以 CPython 另有一个定期运行的“循环垃圾收集器”，Swift 则要求程序员用 weak 打破循环。
      • 追踪式垃圾回收：定期从全局变量、栈上的变量出发，顺着指针把能找到的对象都标记一遍，找不到的就是垃圾。Java、Go、JavaScript 都用它的各种变体。程序员省心，代价是回收时可能有停顿、占用更多内存。追踪式回收器知道所有指针在哪，所以它可以挪动对象做紧凑，这是 C 做不到的。
      • 所有权：Rust 在编译时规定每块内存只有一个“主人”，主人离开作用域就自动释放，借用必须遵守编译器检查的规则。没有运行时的垃圾回收，也不会有泄漏之外的那几种错误（释放后使用、重复释放）。

      头文件写什么

      main.c 要调用 util.c 里的 square，编译 main.c 时编译器只看得见 main.c，它需要知道“有一个叫 square 的函数，参数是一个 int，返回一个 int”，才能检查你调用得对不对、生成正确的指令。这句话叫声明：int square(int x);（没有函数体）。把声明写进一个头文件 util.h，谁要用就 #include 它。函数真正的代码（定义）只写在 util.c 里一份。#include <stdio.h> 也是这样：stdio.h 里只有 printf 的声明，printf 的机器码在系统的 C 库里，链接时才接上。

      符号表和重定位

      每个目标文件都带一张符号表，列出它定义了哪些全局符号（函数名、全局变量名）和引用了哪些别人定义的符号。用 nm 查看：T 是定义在代码段的函数，D 是有初值的全局变量（数据段），B 是没初值的全局变量（BSS），U 是“用到了但没定义”。链接器做两件事：符号解析（给每个 U 找到唯一的定义）和重定位（把各个 .o 的代码和数据排进最终文件，算出每个符号的地址，再把所有引用它的指令里空着的地址填上，目标文件里记着“哪些位置要填、填谁的地址”的重定位表）。

      可见性：static 和 extern

      • 函数或全局变量前加 static，它就只在本文件可见，不进入链接，别的文件有同名的也不冲突。好习惯：不打算给别人用的都加 static。
      • 两个文件都定义了同名的全局函数或有初值的全局变量，链接时报 duplicate symbol（重复定义）。所以头文件里不能写定义，否则被两个 .c 包含就重复了。
      • 多个文件要共用一个全局变量：在一个 .c 里定义 int counter = 0;，在头文件里声明 extern int counter;。
      • 头文件保护：头文件被间接包含两次会出问题，惯用写法是 #ifndef UTIL_H / #define UTIL_H / … / #endif，或者 #pragma once。

      静态库和动态库

      静态库（.a，就是一包 .o）在链接时把用到的代码拷进可执行文件：程序大一些，但不依赖外部文件。动态库（macOS 的 .dylib、Linux 的 .so、Windows 的 .dll）只在可执行文件里记下“我需要它”，运行时才由动态链接器装进内存，多个程序共享同一份：程序小、库升级不用重新编译，但库不在或版本不对就运行不了。macOS 上的 C 库就在动态库 libSystem 里，用 otool -L prog 能看到。

      408 操作系统把链接分为三种：静态链接（运行前链成一个整体）、装入时动态链接（装入内存时边装边链）、运行时动态链接（执行中用到某模块时才链接，例如用 dlopen 打开插件）。对应的“装入”方式见下一章。

      可执行文件里有什么

      macOS 的可执行文件是 Mach-O 格式（Linux 是 ELF，Windows 是 PE），里面按段（segment）分：__TEXT（只读、可执行：机器码 __text 节、字符串常量 __cstring 节等）、__DATA（可读写：已初始化的全局变量、BSS 等）、__LINKEDIT（符号表、重定位信息、代码签名）。用 otool -l prog 看“加载命令”，size -m prog 看各节大小。下一章讲操作系统怎样按这些段把程序放进内存。

      dyld 和共享缓存

      macOS 的动态链接器叫 dyld。为了让几百个系统库加载得快，Apple 把它们预先链接好，合并成一个巨大的“共享缓存”文件，所有程序共享映射。所以在新版 macOS 上，你会发现 /usr/lib/libSystem.B.dylib 这样的文件在磁盘上并不单独存在，它们都在共享缓存里。

      位置无关代码

      动态库每次可能被装到不同的地址（还有第十八章的地址随机化），所以它的代码里不能写死绝对地址。编译成位置无关代码（PIC）：访问全局数据用“相对于当前指令的偏移”（arm64 的 adrp 加 add 正好擅长这个），调用外部函数先跳到一小段“桩”，由它去一张表里查真正的地址，这张表由动态链接器在加载时或第一次调用时填好（Linux 上叫 PLT 和 GOT）。macOS 上的可执行文件默认也是位置无关的，好让整个程序都能随机化地址。

      链接时优化和构建系统

      分开编译的代价是：编译器一次只看一个文件，没法把 util.c 里的 square 内联进 main。链接时优化（-flto）让编译器在链接阶段重新看一遍所有代码，跨文件优化。大型项目不再手写 Makefile，而是用 CMake、Meson 生成构建脚本，用 Ninja 这类专注速度的工具执行；Xcode 有自己的构建系统。

      逻辑地址和三种装入

      编译链接出来的程序，里面的地址都是从某个约定的起点算起的逻辑地址；程序最终在内存里的位置是物理地址。从前者到后者的转换叫重定位。408 操作系统把装入分为三种：

      • 绝对装入：编译时就知道程序会装在哪里，直接生成物理地址。只适合单道程序的简单系统。
      • 可重定位装入（静态重定位）：装入时一次性把程序里所有地址加上装入的起始地址。装好以后不能再移动。
      • 动态运行时装入（动态重定位）：装入后程序里仍是逻辑地址，每次访问内存时由硬件把逻辑地址加上重定位寄存器的值得到物理地址。程序可以在内存里移动（只要改寄存器），这是第二十一章“紧凑”在操作系统层面能做的前提。今天的分页（第二十七章）是它的推广：不是加一个基址，而是查一张表。

      exec 做了什么

      在类 Unix 系统里，“运行一个程序”是系统调用 exec 族（如 execve）完成的：它不新建进程，而是把调用它的那个进程的地址空间整个换成新程序的（代码、数据、堆、栈全部丢掉重来），进程号不变。shell 先 fork 出一个自己的复制品，再让复制品 exec 目标程序，这就是第二十六章的 fork + exec。

      典型题 · 原创

      （1）某程序采用动态运行时装入，被装到物理地址 20000H 开始的区域，重定位寄存器的值是多少？程序中逻辑地址 0345H 处的一条指令访问逻辑地址 1A00H 的数据，实际访问的物理地址是多少？（2）若改为可重定位装入，程序装入后被操作系统移动到 40000H，会出现什么问题？

      看解答

      （1）重定位寄存器 = 20000H；物理地址 = 20000H + 1A00H = 21A00H（这条指令本身在 20345H）。

      （2）可重定位装入在装入时已经把程序里的地址都改成了基于 20000H 的物理地址，移动后这些地址全都指向旧位置，程序会访问错误的内存。所以静态重定位的程序装入后不能移动；要能移动，必须用动态重定位。

      代码签名

      在 Apple Silicon 的 Mac 上，内核拒绝运行没有有效签名的原生代码。你自己编译的 where 能运行，是因为链接器自动给它做了一个“临时签名”（ad-hoc）：只记录了文件内容的哈希，不说明是谁签的。用 codesign -dv where 能看到 Signature=adhoc。如果你用十六进制编辑器改了 where 里的一个字节，签名就对不上，运行时会被系统直接杀掉（终端显示 killed）。发布给别人用的程序，要用开发者证书签名并提交给 Apple 公证。

      隔离属性和门禁

      从浏览器、聊天软件下载的文件，会被打上一个“隔离”扩展属性（xattr -l 文件 能看到 com.apple.quarantine）。第一次打开带这个属性的程序时，门禁（Gatekeeper）会检查它的签名和公证，不合格就拦下，弹出“无法验证开发者”。这是 macOS 防恶意软件的第一道门；遇到它时，先想清楚这个程序是从哪里来的，而不是急着找办法绕过。

      系统完整性保护

      系统完整性保护（SIP）让系统目录里的文件连管理员也改不了，并限制调试器附加到系统进程、限制某些动态链接器的环境变量对系统程序起作用。所以一些老教程里“用 DYLD_ 开头的环境变量注入代码”“用 dtrace 跟踪任何进程”的做法，在默认设置的 Mac 上不再管用。第二十五章要跟踪系统调用时，我们会改用 Linux 虚拟机。

      #! 开头的脚本

      第七章的 hi.sh 能直接运行，是因为内核在 exec 时发现文件以 #! 开头，就读出后面写的解释器路径（比如 #!/bin/zsh 或 #!/usr/bin/env python3），改为运行那个解释器、把脚本文件名作为参数交给它。脚本本身不是机器码，所以也不需要第二十二章的那四步。

      找虫子的四步

      程序里的错误叫 bug（虫子），找错误叫调试（debug）。据说这个词和 1947 年一台计算机里真的夹住的一只飞蛾有关（《一块一块》里讲过，那只飞蛾被贴在了工作日志上）。不管多厉害的程序员，调试都按这几步：

      1. 复现：先找到一个每次都能让错误出现的输入。时有时无的错误最难查，先想办法让它稳定出现。
      2. 缩小：把范围缩小到最少的代码。程序的前一半有没有问题？把输入减到最短还会错吗？
      3. 假设：根据看到的现象，猜一个原因。“平均数太大，可能是加进了不该加的数。”
      4. 验证：让程序停下来，看变量，证明或推翻你的猜测。推翻了就换一个猜测。

      最简单的“看变量”是在代码里加 printf，把中间结果打出来。它很好用，但每看一个新变量都要改代码、重新编译。调试器能让程序停在任何一行，随便看任何变量，还能一步一步往下走。Mac 上的调试器叫 lldb，它和 clang 是同一个项目（LLVM）里的工具，装命令行工具时已经装好了。

      断点的秘密
      
      
      你在第 5 行设断点时，lldb 查调试信息，找到第 5 行对应的第一条机器指令的地址，然后把那条指令换成一条陷阱指令（arm64 上是 brk #0，x86 上是 int3），原来的指令先存起来。程序跑到那里，执行陷阱指令，处理器产生异常，操作系统暂停这个进程并通知调试器。你输入 continue 时，调试器把原指令放回去、单步执行这一条，再把陷阱指令换回来，让程序继续跑。所以“断点”其实是调试器在你的程序里偷偷改写了代码（第十三章“指令即数据”的又一次应用）。
      
      
        
        
      • 单步：处理器有专门的“单步”模式，每执行一条指令就产生一次异常，调试器借此一条一条地走。
        • 
        
      • 硬件观察点：处理器里有几个调试寄存器，可以设置“访问这个地址就产生异常”，不用改代码、不拖慢程序，但数量很少（通常只有几个）。超过数量时，调试器只能用慢得多的软件办法。
        • 
        
      • 控制另一个进程：调试器要读写别的进程的内存和寄存器，需要操作系统给它特权（Linux 上是 ptrace 系统调用，macOS 上是 Mach 的任务端口）。所以 macOS 会要你输入密码授权，系统进程则受第二十三章的系统完整性保护，不让调试。
        • 
      
      
      
      调试信息
      
      
      -g 让编译器生成 DWARF 格式的调试信息：哪个地址对应源文件第几行、每个变量放在哪个寄存器或栈上的哪个位置、类型是什么。在 Mac 上，它们留在 .o 文件里，可执行文件只记着去哪找；发布时用 dsymutil 把它们收集成一个 .dSYM 包，崩溃报告靠它把地址翻译回函数名和行号（叫“符号化”）。开了优化（-O2）以后，变量可能只活在寄存器里、甚至被算掉了，代码行也被重排合并，调试器常显示 “optimized out”，这就是调试时用 -O0 的原因。
